# 音声の途切れ調査と Version 1.13 / 1.14

## 確認できた事実

- 2026-10-05 の実行中EXEは Qt 6.11.1、実処理プロセスは `AboveNormal`。
- 音声デバイスへ転送する `QWASAPIAudioSinkStream` は優先度22で動作していた。
- その手前の `QFFmpeg::AudioRenderer`、`QFFmpeg::StreamDecoder1`、`QFFmpeg::Demuxer` は通常のスレッド優先度（相対0、ベース10）のままだった。
- 既定出力は `FA620BT`。PnP上はUSB音声機器であり、名前からBluetooth接続とは判断できない。
- 現行ソース/Version 1.12には、全曲RAM先読み完了を待って `setSourceDevice()` する処理が残っていた。これは曲開始の待ち時間を生むが、出力スレッドのスケジューリングやUSB転送の遅延を解決するものではない。
- QtのFFmpeg実装は約110msの出力バッファを確保し、約22～64msの音声供給量を目標に調整する。ファイル全体をメモリへ置くこととは別の層である。

## 対策

- 全曲RAM先読みを取り除き、Qtのファイル直接再生に戻した。新しいバッファ充填待ち、固定待ち時間、次曲全体の先読みは加えていない。
- Windowsでは音声供給の3種類のスレッドだけを `THREAD_PRIORITY_HIGHEST`（相対2）へ上げる。既存のプロセス `ABOVE_NORMAL` と組み合わせてベース12となる。リアルタイム優先度は使わない。
- QtのWASAPI/MMCSSスレッド、GUI、画像処理、HTTP、ビデオデコードの優先度には触れない。
- 再生中だけ `timeBeginPeriod(1)` を要求し、プロセスの実行速度・タイマー精度の省電力制御を明示的に無効化する。一時停止、停止、無効なメディア、終了では要求を解放し、元の電力ポリシーに戻す。
- 曲・デバイス切り替えで再生成されるスレッドを再確認する。Windows APIが使えない場合も通常の再生を継続し、ログへ失敗を記録する。
- バージョンの正は `_conf/app_version.xml`。Version 1.12から1.13へ更新し、互換JSON、配布用情報、フォールバック値を同期。

## 検証

`python -m unittest discover -s tests -v`：10テスト成功。

- 実Qt/WAVのデコード、次曲開始、Pythonでの全曲読込不要、シーク、ワンショット復帰、連続切り替え、リピートを確認。
- 音声供給スレッドの実際のWindows優先度が2以上であることを読み返して確認。
- 一時停止/停止/無効ファイルでタイマー要求を解放し、電力ポリシーを復元することを確認。
- 無負荷の次曲最初のデコード音声データは約76ms。

実MP3で、テスト用プレイヤーとCPU負荷を2コアに限定し、6つの計算プロセス（AboveNormal）と隔離したheadless Edgeの起動を重ねて12秒間比較した。既存の常駐プレイヤーの再生/出力設定は変更していない。出力はミュート。

| 測定項目 | 旧実装 1.12 | 修正実装 1.13 |
| --- | ---: | ---: |
| 音声デコード通知数 | 500 | 500 |
| 通知の最大間隔 | 26.3ms | 26.0ms |
| 100ms超の通知間隔 | 0 | 0 |
| 再生位置の進行 | 11,976ms | 12,024ms |
| 次曲の最初の音声データ | 377.1ms | 188.1ms |
| GUI処理の最大間隔 | 35.3ms | 196.3ms |

この比較は両方ともローカルのQt 6.11.2で行った。1回の測定であり、固定性能を保証する数値ではない。GUIは強い負荷で遅れる場合があるが、この測定では音声供給は継続した。

## 原因の確度と残る確認

音声供給スレッドが負荷の影響を受ける構造と、全曲先読みによる開始待ちは確認済み。今回の対策はこの構造を改善する。

ただし、上記負荷試験では旧実装でもユーザー申告の激しい途切れは再現しなかった。デコード通知と再生位置は、USBドライバー以降の実際の音声波形を保証しない。したがって「ノイズの根本原因を特定・完全解消した」とは断定しない。

システムログではFA620BTを指す音声/USB障害は見つからなかった。別機器のKernel-PnP 219は因果関係が確認できず、原因とは扱わない。単発のCPU/DPC統計にも異常は見つからなかったが、短いDPC遅延を除外できるものではない。

Windows Performance RecorderのAudio/CPUトレースも試みたが、システム性能プロファイル有効化が `0xc5585011` で失敗し、カーネルトレースによる確定には至っていない。

新EXEを完全終了後に起動して実際のブラウザ起動・利用中の音を確認する。症状が残る場合は、発生時刻とアプリログを照合し、WPR Audio/CPUでDPC/ISR、USBドライバー、音声エンジンの遅延を確認する必要がある。OS・ドライバー・音声機器の設定変更は今回行っていない。

## Version 1.14：表示切り替え時の追加調査

ユーザーの実音確認では1.13で「軽くなったがまだ途切れる」。さらに自分自身の小型/通常表示の切り替えでも発生することが分かったため、調査を継続した。

実Windowsウィンドウで表示を16回切り替えるテストを実施した。再生状態や出力デバイスの変更通知は発生せず、ウィンドウIDも同じだった。したがって、切り替えが意図せず再生を停止したり、ウィンドウを破棄したりすることはこの試験では確認されなかった。

QAudioBufferOutputのPython観測コールバックでは最大127.2msの間隔が見えた。ただしこのコールバック自身がGUIとPythonのGILを共有するため、これをそのまま実出力の欠落とは扱えない。別プロセスのWASAPIループバックで、非既定のRealtek出力に低音量の既知信号を出し、16回の切り替えを測定したところ10ms単位の無音欠落はなかった。既定FA620BTの測定は他の再生音が混ざったため、欠落の有無を断定できない。ループバックは物理USB転送後の波形を測るものでもない。

一方、次の余分なGUI処理は確認できた。

- 小型/通常表示の切り替えが毎回QSettings.sync()を同期実行していた。2曲でも約50ms掛かる場合があった。
- ドロワーが表示中というだけで、resize/show経由から分割位置復元を再予約していた。
- 復元要求ごとに0/150/500msの3本のタイマーを生成し、小型へ切り替えた後にも旧予約が実行されていた。
- 多数のコントロールの表示・非表示、枠・サイズ変更、画像拡縮の途中状態にも再描画/resize処理が重なっていた。

1.14では表示変更を一括で適用し、途中状態の再描画とresize連動処理を抑制した。最終レイアウトの画像拡縮は一度だけ予約する。設定保存は750ms後へまとめ、表示切り替えの同期経路からディスク書込みを除いた。分割位置復元はドロワーが開く時だけ、所有する1本の150msタイマーへまとめ、小型表示中は取り消す。音声ソース、再生状態、バッファサイズは変更しない。

実際の696曲の設定を隔離コピーして実Windowsウィンドウで比較した結果：

| 16回の表示切り替え | 1.13 | 1.14 |
| --- | ---: | ---: |
| 分割位置の復元要求 | 18回（3本ずつ予約） | 8回（1本へ集約） |
| 切り替え処理の最大時間 | 80.5ms | 30.9ms |
| Python音声観測コールバックの最大間隔 | 67.5ms | 40.5ms |

単発比較の結果であり、実スピーカーからのノイズ解消を保証するものではない。GUI操作中の余分な処理と同期I/Oを減らしたことは確認できた。

回帰テストは13項目成功。表示切り替えが音声ソースやPlayingStateを変更しないこと、同期保存を呼ばないこと、既存ドロワーの更新で復元を再予約しないこと、20個の復元要求が1回にまとまること、保存した分割比率が反映されることも検証した。WAVの次曲の最初のデコード音声データはこの試験で125.8msだった。


過去の配布ZIP `release/DropMP3-Portable-Ver1.02-x64.zip` 内のEXEからQt6Core.dllのPEバージョンを読み出したところ、Qt 6.11.1.0だった。v1.08時点のGitソースにも同期保存/3本の復元タイマーは存在した。したがって、これらが今回初めて導入された、またはQtの更新だけが最近の悪化の原因だった、とは判断しない。負荷に弱い既存処理を削減したが、最近悪化した理由の確定には症状発生中の追加観測が必要である。

小型/通常表示のスクリーンショットでも画像、再生コントロール、時間、ドロワーを確認した。


### 手動のダブルクリックで再生が一時停止する不具合

ユーザーから「短い間隔の自動切り替えでは途切れないが、マウス操作ではノイズ・途切れが出る。長めの切り替え間隔で確認してほしい」と追加情報を得た。

自動試験は表示関数を直接呼び、マウス処理を通っていなかった。ArtLabelのマウスイベントを通して調べると、Windows/Qtのダブルクリック判定時間はこのPCで500msなのに、アプリの単クリック確定は220ms固定だった。1回目のクリックから300ms待ち、2回目のダブルクリックイベントを送ると、旧処理では先に単クリックが確定し、PlayingStateからPausedStateへ変わった。表示切り替えだけのはずの操作で一時停止してしまう、不具合を再現できた。

単クリックの確定待ちを `QApplication.doubleClickInterval() + 20ms` とし、早く発火しないPreciseTimerに変更した。ダブルクリックは単クリック予約を取り消す。OS設定は書き換えず、毎回読み取る。画像の単クリックでの再生/停止はこの判定後に実行するため、このPCでは約520ms待つ。再生ボタンや曲の開始にこの待ちは追加しない。

同じ300msの操作で、修正後はPlayingStateを保って小型表示へ切り替わり、単クリック/再生状態変更とも0回だった。

要求された長めの間隔でも、実Windowsウィンドウ・696曲設定・実MP3に対し、300ms間隔のダブルクリックを4秒ずつ空けて6回実施した。Pythonのデコード観測コールバックは外して測定への影響を避け、出力はミュート。単クリック0回、ダブルクリック6回、再生状態変更0回、約29秒の試験で再生位置は27,559ms進んだ。6回ともPlayingStateのまま、通常/小型表示が交互に切り替わった。

回帰テストは15項目成功。遅めのダブルクリックで一時停止しないことと、意図した単クリックで1回だけ一時停止できることも確認した。次曲の最初のデコード音声データは同試験で123.6ms。

この誤一時停止は再現・修正したが、ブラウザ起動中のノイズや、すべての手動切り替えノイズがこれだけで説明できるとは断定しない。ユーザーの実音での再確認が必要である。

参照：[Qt QApplication.doubleClickInterval](https://doc.qt.io/qt-6/qapplication.html#doubleClickInterval-prop)。

## Version 1.15：再生プロセスの分離

1.14を実機確認していただいたが、回答は「変わらずノイズ・途切れが出る」。重いブラウザサイトほど悪化し、通常/小型のどちらへの切り替えでも発生する。GUI軽量化と誤一時停止修正だけでは実音の問題を解消できていない。

### 今回の構成

- QMediaPlayer、実際に鳴らすQAudioOutput、音声スケジューリング対策を、QCoreApplicationだけの常駐プロセスへ移動。再描画、画像処理、設定保存、GUIのPython GILを共有しない。
- GUIからは非同期のローカル名前付きパイプで操作し、位置/長さ/状態を受け取る。同じユーザーだけのアクセス権とランダム名を使い、接続後は待受けを閉じる。公開TCPポートは追加しない。
- 再生プロセスは起動時に作成し、次曲・リピート・一時再生でも同じPIDを使う。全曲先読み、先読み待ち、PCMバッファ増量、曲ごとのプロセス起動は加えていない。
- 親の終了/強制終了でパイプが切れれば再生側も終了。明示終了はquit後に待ち、応答しない自分の子プロセスだけを回収する。
- 世代番号で旧曲のイベントが新曲へ混ざるのを防ぐ。同じURLのリピートではQtが長さ変更を通知しないため、ソース操作直後の状態を明示送信する。
- 再生側だけHIGH_PRIORITY_CLASS、GUIは従来のAboveNormal。REALTIME/TIME_CRITICALは使わない。再生側はUI・画像・HTTP処理を持たない。
- 再生中だけ1ms精度要求と電力抑制解除を適用し、停止/一時停止で解放。供給3スレッドの相対優先度2とWASAPIのMMCSS処理を継続。
- 長さ0の通知で保存位置の復元を消費しないようにした。音量・ミュート・出力デバイス変更も再生側へ送る。

### 検証

実Qt回帰テスト19項目成功。次曲開始、シーク、一時再生からの復帰、連続曲変更、リピート、同一URLの長さ保持、自然終端、表示切り替え、実スレッド優先度、電力ポリシー復元、子プロセス再利用/回収などを確認した。

| 試験 | 結果 |
| --- | --- |
| WAV次曲の最初のデコード音声データ | 74.5ms |
| 自然終端で前曲の最終通知から次曲の最初まで | 134.6ms |
| GUI/GILをbusy loopで0.800秒塞ぐ | 再生側の実デコード通知9回、最大間隔86.3ms（WAVの4096フレーム単位） |
| 実696曲設定・300ms間隔のダブルクリックを4秒ずつ空け6回 | 全てPlayingState、単クリック0、状態変更0、26.19秒で26,160ms進行 |
| 2コア制限、6計算プロセスAboveNormal、重いheadless Edge、4秒間隔のマウス切り替え7回 | 約29秒で1,207デコード通知、最大間隔51.6ms、100ms超0回、位置28,992ms進行、状態変更0 |
| 上記の強い負荷下の次曲開始 | 186.7ms |
| 親だけの強制終了 | 再生側も5秒以内に終了、孤立なし |

再生側がAboveNormalの段階では、強い負荷条件で次曲開始831.8msのケースが見つかった。供給スレッド生成前の制御処理も保護するため、再生専用プロセスの優先度を上げた。HIGHへの変更後に上記開始時間を確認した。

音声の観測時刻は再生側で取得し、GUIの受信時刻は使わない。GUIループの最大間隔には試験自体の300msクリック待ちが含まれるため、GUI処理時間とは扱わない。

これらはデコード/操作/継続性の検証で、USB転送後の物理音やスピーカーのノイズ解消を保証しない。ユーザーの実音確認を基準にする。OSのDPC/ISRや出力機器の遅延まで除去できるとは断定しない。開始時間は単発実測で固定保証ではない。

参照：[Microsoft SetPriorityClass](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setpriorityclass)、[Qt QLocalServer](https://doc.qt.io/qt-6/qlocalserver.html#SocketOption-enum)。

## Version 1.16：字幕の再描画と音声供給のMMCSS

v1.15の実音回答は「だいぶ良くなったが、まだ少しだけ途切れる。拡縮では出にくくなっている」。重いサイトでの途切れと、歌詞字幕表示との関係も報告された。完全解消とは扱わず追加調査した。

### 字幕

字幕は曲位置が同じ行を指す間は再描画しない実装だったが、行の変更ごとにupdate()で透明な画像全体を無効化していた。背後の画像も全体が再描画されることを実QPaintEventで確認。字幕のない間隔でもウィジェットのshow/hideが発生し、画像全体を無効化していた。

- 字幕枠だけのDPI対応QPixmapを生成・再利用。内容、スタイル、サイズが変わったときだけ折返し/文字描画を作り直す。
- 更新領域を前後の字幕枠の和集合に限定し、前の行の残像も消す。字幕間の空白は透明にして、表示中のキャンバスをshow/hideしない。ユーザーの字幕非表示操作は従来どおり隠す。
- 隠れている字幕の画像生成は行わない。露出による再描画では既存画像を使う。
- 見た目の内容・行配置・設定フォント/色/位置を維持。透明な画像への文字キャッシュによりアンチエイリアスの画素値は元の直接描画と完全同一ではないが、スクリーンショットでレイアウト・可読性を確認。

1100×900、50回の行切り替えを実Windowsウィンドウで比較：

| 指標 | 1.15 | 1.16 |
| --- | ---: | ---: |
| 字幕・背面画像の平均再描画面積 | 各990,000px | 各85,337.88px |
| 合計の更新/描画時間 | 837.4ms | 382.4ms |
| 最大更新/描画時間 | 73.7ms | 44.3ms |

再描画面積は約91.4%減少。単発比較であり、初回フォント処理やOSの負荷の影響を受けるため時間短縮の保証ではない。

### MMCSS

Media FoundationにはMMCSS対応の作業キューを使う仕組みがある。標準プレイヤーの個々の内部バッファ量まで確認できたわけではない。このアプリではQtのWASAPI出力はMMCSSでbase priority 22だったが、FFmpeg側の供給は15だった。

QAudioBufferOutputのDirectConnectionがQFFmpeg::AudioRendererの実スレッドで呼ばれることをQtソースと実際のQThread名/Thread IDで確認。そこでAudioタスクへ登録し、AVRT_PRIORITY_HIGHを適用する。登録は一度だけ、PCMのPythonコピー/送信はしない。Qtの内部スレッド名が一致しない場合は登録しない。

同じネイティブスレッドのfinishedでAvRevertMmThreadCharacteristicsを呼ぶQObjectを保持し、MMCSS登録を回収。通常の供給優先度更新はMMCSS登録済みのレンダラーへ上書きしない。デマルチプレクサとデコーダの相対優先度2は維持。GUIをMMCSSへ登録せず、Windowsのサービス/レジストリも変更しない。

隔離した実Qtスレッドで5回登録・終了を繰り返し、全て同じThread IDで解除成功。登録API処理は0.055～0.106ms。base priorityは22（通常プロセスで相対14）、配布時はHIGHプロセスで相対9に相当する。

### 検証

- 回帰試験23項目成功。字幕の限定更新、空白で透明画像へ戻ること、ユーザー非表示、文字レイアウトの再利用とスタイル変更、GUIへのMMCSS誤登録防止、実レンダラー3回の登録/解除も検証。
- この実測のWAV次曲開始192.0ms、自然終端から次曲の通知155.7ms。固定待ち・全曲先読み・出力バッファ増量は追加しない。
- GUI/GILを0.800秒塞いだ間の音声通知は9回、最大86.5ms。
- 2コア・6計算プロセス・29秒の重いheadless Edge・4秒間隔のマウス表示切り替え7回に字幕行切り替えを追加。1,217音声通知、最大26.8ms、100ms超0、位置29,208ms進行、状態変更0、次曲開始130.6ms。旧レンダラーのMMCSS解除と新レンダラー登録もログで確認。

### OSとメモリの追加観測

v1.15再生中の60秒を、外部プロセスからQueryThreadCycleTimeと100ms間隔のPDHで観測。音声レンダラーの実行変化間隔最大25.07ms、WASAPI最大14.017ms、観測ポーリング最大5.22ms。各CPUのDPC Time最大31.27%（CPU0）、Interrupt Time最大46.18%（CPU10）、Processor Time最大100%を観測した。平均区間の値であり、特定ドライバーのDPC時間、音声バッファ欠落、申告時刻との一致を確定するものではない。こちらの隔離UI検証も含む時間帯なので、ブラウザ単独の影響とは断定しない。

メモリ交換の質問に対し、CIM/SMBIOSから実構成を確認。i5-14500、MSI PRO B760M-A DDR4 II、16GB×4=64GB、A-DATA×2/Samsung×2で両コントローラーに配置。全DIMMのSpeed/ConfiguredClockSpeedは3200、ConfiguredVoltageは1200mV。低い設定へ落ちている兆候はない。過去14日のWHEAイベント0件も確認。ただしSMBIOSの申告は実時計測や完全なメモリ健全性検査ではなく、エラー記録がないことだけで故障を除外しない。BIOS/XMP/メモリ交換などの設定変更は行っていない。

## 1.17: Windows Media Foundation の再生経路

### 再現条件と判断

ユーザーは重いサイトに加えて、VS Code の最小化・最大化で本アプリが確実に途切れると報告。Windows 11 メディアプレイヤーは途切れず、同時再生しても本アプリだけ途切れることを確認済み。1.16 の改善では残るため、Qt/FFmpeg の音声供給経路と Windows 標準の再生経路との差を優先して対処する。特定のドライバー/DPCやメモリ故障を原因と断定したものではない。

### 実装

- Windows では WinRT の Windows.Media.Playback.MediaPlayer / Media Foundation を使用。GUIから独立した既存の常駐音声プロセスに組み込み、曲ごとのプロセス起動はしない。
- StorageFile の非同期オープンで日本語のローカルパスを扱う。QUrlのスラッシュはPathでWindows形式へ戻す。ファイル全体をPythonで読み込まず、固定の先読み待ち・追加の出力バッファ増量は導入しない。Windows内部のバッファ量はOSが管理する。
- WinRTイベントはQtのキューを通して音声プロセスの制御スレッドへ戻す。曲ごとの世代を確認し、古い曲のイベントと非同期オープン結果を破棄する。
- 音量・ミュート・シーク・停止・自然終端・再開を既存のQt互換IPCへ変換。Windowsの音声エンドポイントとQtのデバイスIDを照合し、選択出力先を保持する。Windowsのメディアコマンド管理は無効化し、既存UIの操作を使う。
- Native初期化または形式の読み込み失敗時は同じ曲をQtで再試行する。診断statusにaudio_engineを追加し、実際にどの経路が動いているかを識別できる。Qtへの切り戻しはログにも記録する。
- PyWinRT 3.2.1 の必要な8パッケージを同じABIバージョンに固定し、requirementsとビルドスクリプトに追加。実行ファイルへも同梱する。

### 検証と限界

- Qtの実デコード回帰試験23項目成功。Qtを明示選択して検証するため、Windows経路の再生をQtのPCM通知と誤認しない。
- Windows実再生試験6項目成功。日本語ファイル名、同一ファイル再選択、曲送り、自然終端からの次曲、オープン前シーク、一時停止/再開/停止、GUIのPython処理を0.8秒占有、無効ファイルのエラー、全列挙出力先のエンドポイント照合を確認。
- WAVの再生位置が進み始める通知まで128.6 / 142.9 / 136.0 / 140.2ms。自然終端から次曲の進行通知まで121.8ms。これらはセッション位置の通知時間であり、物理出力の最初のサンプルを録音した値ではない。
- 実MP3の繰り返し再生・10秒シーク・一時停止/再開もWindows経路で確認。
- 2コア、6計算プロセス、重いheadless Edgeを29秒、4秒間隔の手動相当マウス表示切り替え7回と字幕描画の負荷試験：再生位置28,994ms進行、状態変更0、次曲の進行通知170.7ms、GUIの曲送り処理45.1ms。位置通知は最大129.6ms間隔、GUIループ最大458.2ms遅延。これは音声の欠落を直接計測したものではなく、表示の遅延から音の停止を断定しない。
- ユーザーのVS Code操作による実音の再確認が必要。自動試験の成功だけで解消済みとは扱わない。
